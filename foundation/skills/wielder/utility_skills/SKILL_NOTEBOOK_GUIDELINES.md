 Jupyter Notebooks & Data Exploration

[Read Strict FS Agnosticism](../data_skills/SKILL_STRICT_FS_AGNOSTICISM.md) when notebooks or companion scripts read, write, display, preview, or link bucket objects, table outputs, Spark artifacts, materializations, or provider URIs.

- **Explore Intent**: In `explore/`-style notebook spaces, notebooks primarily exist for curiosity, analysis, and QA. They are allowed to be WET and investigative; the goal is to make real artifacts and behaviors legible, not to force exploratory work into production-shaped abstractions.
- **Notebook Placement**: Exploration notebooks belong under the repository's `explore/` tree, not inside production app modules. Keep production app directories for reusable code, configs, tests, and docs.
- **Topical Organization Guideline**: Within `explore/`, prefer grouping by topic or investigation surface such as `model_runtime/exploration/` or `data_preparation/search/` rather than by production app module. Treat this as a lightweight guideline for readability, not a rule that should slow down or block exploration.
- **Naming**: Do not include `wet` or `notebook` in notebook filenames. Notebooks in `explore/` are already allowed to be WET and the `.ipynb` extension already says notebook.
- **Reader-First Opening**: Open every notebook with a Markdown explanation cell before imports. Give the reader the title, dataset or subject, question, concise method, and important interpretation boundary before exposing implementation. Keep historical decision rationale in the experiment or study document unless it is necessary to interpret a displayed result.
- **Displaying DataFrames**: Always use a scrollable frame utility (e.g., `from wielder.visual.display import display_scrollable_dataframe`) instead of raw `.head()` or `.tail()`. This prevents IDE DOM thrashing.
- **DataFrame Nomenclature**: Name Spark DataFrames with an `_sdf` suffix and pandas DataFrames with an `_df` suffix. When previewing Spark results interactively, create the Spark DataFrame first, then materialize only the first configured `N` rows into pandas and display that bounded pandas DataFrame with the scrollable frame utility.
- **1 Display Per Cell**: A single code cell MUST NOT contain multiple visual output calls to avoid crashing the DOM.
- **Compute → Explain → Display**: Present every reader-facing table or visualization as three adjacent cells in this order: (1) a code cell that computes or prepares the result, (2) a Markdown cell that explains the result immediately below the computation and immediately above the output, and (3) a minimal code cell that only displays the table or renders the visualization. Treat the explanation and output as one visual unit: the reader must not need to scroll or remember distant prose to interpret what is on screen. Do not place loading, transformation, or other computation between the explanation and its output. Give every output a descriptive name and state what one row or point represents, what the principal metric means, and how to interpret important markers, colors, or boundaries.
- **Minimal Output Cells**: Keep the code cell beneath a table or figure explanation to one short display or plotting call whenever practical. Move repeated plotting loops, layout mechanics, and formatting into honestly named helpers defined earlier in the notebook or companion script. Keep scientific calculations visible in the preparation cells; do not bury substantive analysis inside a presentation helper merely to shorten the output cell.
- **Script-to-Notebook Duality**: Scripts and Notebooks MUST remain fluid. NEVER manually copy-paste cells. 
  - Python files MUST be strictly delineated by `# %%` block markers. 
  - Aggressively replace `# In[ ]:` cell artifacts with `# %%`.
  - Compile WET codebase translations via Wielder conversion utilities instead of arbitrarily editing internal JSON abstractions.
- **Centralized Notebook Configuration Block**: Exploration notebooks SHOULD expose their topographical modes and target selectors in one early configuration cell. Keep `ecosystem`, `stage_tier`, and adjacent mode toggles together so a reader can quickly retarget the notebook for data exploration without hunting through downstream cells.
- **Notebook User Selector Overrides**: When a companion script backs an interactive notebook, name explicit user-controlled target selectors with the `notebook_user_selected_*` prefix in the early configuration cell (for example `notebook_user_selected_input_index` or `notebook_user_selected_input_key`). These selectors MUST override configured legacy defaults or discovered convenience matches. Companion scripts may display configured values such as `source_filename`, but they MUST NOT silently replace a non-null notebook user selector with a config-derived choice downstream.
- **Data Notebook Links**: For ingestion, harmonization, materialization, or backfill notebooks, read and follow `../data_skills/SKILL_DATA_INGESTION_GUIDELINES.md`, `../data_skills/SKILL_HARMONIZATION_GUIDELINES.md`, and `../data_skills/SKILL_PYSPARK_GUIDELINES.md` in addition to this notebook skill.
- **Native Output Truth Boundary**: Exploration notebooks MUST distinguish input materialization, resolved config, sidecars, native model/tool outputs, harmonized tables, and serving materializations. Do not use fixture native files, fake preparation outputs, synthetic score tables, mock prediction rows, or generated success markers as a teaser for real model execution. If native output is absent, show the absence explicitly before any visualization or downstream table preview.
- **BioContext Biochem Canonical Structure View Extension**: In BioContext Biochem molecular-topology notebooks, **Canonical Structure View** is the structure view surface for harmonized `ComplexStructureSet` outputs. Put one Canonical Structure View picker, embed, or handoff cell as high as possible in each relevant notebook, preferably immediately after the title/import/config selector area. If a notebook has multiple possible visualizations, choose one Canonical Structure View route near the top and leave secondary views lower in the notebook. If a notebook is input-focused or table-heavy and cannot honestly render a structure yet, include a short high-up handoff to `explore/molecular_topology/topological_prediction/complex_structure_cif_mmcif_viewer.ipynb` instead of inventing a weaker inline preview.
- **Bucket/Key Display Discipline**: Data notebooks should display bucket plus relative keys, base keys, artifact subkeys, table keys, hydrator kind, and hydrator version. Do not hardcode local bucket roots or duplicate path joins in notebook cells. Use configured accessors/helpers to expand a key only at the read boundary.
- **Strict FS-Agnostic Notebook Outputs**: Notebook companions and converted scripts MUST treat Bucketeer/Spark/catalog URIs as opaque. Do not convert an output URI into `Path(uri)`, derive a parent directory, or print a local HTTP `serve_command` from a generic notebook/test surface. Display `bucket`, `object_key` or table id, and `object_uri` separately. A local preview command is allowed only in a clearly local-only companion cell or selector whose name and config make that limitation explicit.
- **Spark Lookup Preview**: When a notebook explores a scalable table product, include a bounded Spark-backed lookup or projection before pandas inspection. Name the Spark DataFrame with `_sdf`, materialize only a configured or small limit into a `_df`, and display that preview with `display_scrollable_dataframe`.
- **Anti-Pattern: Defensive Execution Skips**: Interactive notebook blocks MUST NOT rely on protective Python constructs (`if`, `try`, `assert`) to artificially bypass empty states (e.g., `if not df.empty:`). If target payloads are missing, the physical execution block MUST crash organically and distinctly dump a python `std-out` stacktrace. Defensive error-handling suppresses immediate visibility inside Jupyter shells.
- **Wielder Notebook Conversion Protocol**: When editing a Jupyter Notebook, you MUST NOT edit `.ipynb` JSON strings or rely on generic third-party plugins. Instead:
  1. Convert the active `.ipynb` into a flat `.py` script using: `python -m wielder.util.notebook_converter <notebook.ipynb>`.
  2. Implement architectural changes natively against the generated `.py` script.
  3. Execute testing directly against the python interpreter.
  4. Once stable, translate the Python definitions back into `.ipynb` cells using `python -m wielder.util.notebook_converter <script.py>`. This specialized parser ensures `# %%` execution blocks and `if __name__ == '__main__':` scaffolds are compiled gracefully natively inside Workspace without structural `.ipynb` indention shifting.

- **Notebook Import Hierarchy**: All Python imports MUST be strictly hoisted to the first code cell after the reader-first Markdown opening (no inline/scattered imports). They must be categorized in the following exact descending order:
  1. Standard lib (`os`, `sys`, `json`, `datetime`)
  2. Common data/ML packages (`numpy`, `pandas`)
  3. Scientific packages (`MDAnalysis`, `py3Dmol`, `rdkit`)
  4. Other external dependencies
  5. `wielder` ecosystem
  6. `workspace` ecosystem
