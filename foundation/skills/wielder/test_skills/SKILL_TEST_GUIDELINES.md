 Testing Constraints & Live QA Protocols

- **The Live Execution Rule**: Tests assessing integration interfaces, Data Lake endpoints, or stochastic Large Language Models (LLMs) MUST inherently execute live data schemas. You MUST NOT use `unittest.mock` to artificially spoof remote model APIs or PySpark IO logic. If it interacts with reality, you verify reality.
- **Anti-Pattern: Synthetic Native Success**: Tests MUST NOT fabricate plausible native model/tool outputs and then treat them as proof that the app ran. Do not use a mock binary, bypass flag, fixture branch, or hand-authored artifact to write native success markers, native result files, prepared feature files, score tables, prediction rows, or report outputs under the app's real output contract. A test may materialize input packages, resolved config sidecars, parser-only fixtures, or expected-failure evidence, but the status and artifact names must say so plainly and assertions must prove that native success is absent until the real configured executable, service, or model produces it.
- **Load-Test Supremacy**: The primary philosophy of Wielder's testing doctrine is that a true load test is fundamentally superior to isolated integration and unit tests. In fact, integration and unit tests are simply down-scaled modulations or subsets of a primary load test. Tearing down and reprovisioning a complete local environment qualifies directly as an integration test, just as deploying to an ephemeral cloud topology with restricted dataset sizes does. The infrastructure and validation rigor remain identically pure—only the scale and topological dimensions change.
- **No Transient Physical Roots**: Treat `/tmp` bucket roots and machine-specific home paths such as `/home/<user>/...` for integration, harmonization, notebook, Spark, or materialization tests as antipatterns. Test mode is a dev-tier scenario overlay, not a disposable filesystem escape hatch. Live test outputs MUST land in configured dev-tier buckets and configured relative keys through the same Bucketeer, Spark, accessor, and Wielder app contracts used by the real endpoint. Operator-facing commands may use `$HOME/...`; config should use the project HOCON home/accessor contract such as `${HOME}` or a resolved bucket/key path. Process-private scratch files are acceptable only when they are not observable app outputs, table URIs, native artifacts, or materialized products.
- **Strict FS-Agnostic Evidence**: Test fixtures and evidence reports must remain valid when the same ecosystem points at local buckets, mounted volumes, S3, GCS, or a remote desktop session. Tests should assert and log provider-neutral bucket names, relative object keys, table/catalog ids, watermarks, and opaque URIs. They MUST NOT derive local paths from URIs, print local preview/serve commands from generic test code, or hide local-only behavior behind Bucketeer, Spark, factories, or helper accessors.
- **Watermarked Test Outputs**: Any live test or fixture backfill that writes durable bucket objects, tables, topics, jobs, or materializations MUST carry a cleanup watermark. The watermark should include at least `test_mode=true`, stage tier, ecosystem, app, scenario or fixture id, run/event id, writer version, created-at timestamp, and cleanup policy or TTL. Prefer a sidecar manifest or catalog row when the output format cannot carry metadata natively.
- **Tethered Cleanup Contract**: Tests that put data in place MUST expose a matching Wielder cleanup surface. `plan-delete -t` should discover watermarked outputs through the same backfill/discovery/accessor functionality used to create or catalog them and log the exact bucket, key, table, partition, topic, job, or materialized bundle that would be removed. `delete -t` should remove only those watermarked test outputs. Cleanup must not rely on broad path deletion, current-date guesses, or manual `/tmp` pruning.
- **HOCON-Owned Data Fixtures**: Tests that require a durable data identity, such as a search UUID, batch name, DAG, target, job, or table slice, should declare that identity in an owning test-mode HOCON fixture rather than depend on an incidental existing bucket object or a current date partition. The semantic fixture and its configured storage contract belong in HOCON under the app or ecosystem test mode directory. If the referenced artifact is absent, the fixture should create it by running the real app/service/runner path at the smallest safe scale, watermark the outputs, then assert by resolving through the service/accessor contract rather than reconstructing storage keys in the test.
- **Wielder Test Mode as Scenario Overlay**: The Wielder `-t/--test` mode is the standard way to make live test fixtures available to any Wielder endpoint that uses the canonical parser and accessor. It is not a pytest-only flag and not a separate action. It selects test overlays while preserving the normal endpoint/action surface, so the same script can be run as `-w plan -t`, `-w apply -t`, or `-w delete -t` against a configured test scenario. See [Configuration Guidelines](../config_skills/SKILL_CONFIGURATION_GUIDELINES.md) for overlay precedence and [Wielder Scripting & Evaluation Skills](../script_skills/SKILL_WIELDER_SCRIPTS.md) for endpoint propagation.
- **Test Mode Fixture Shape**: Ecosystem-scoped system fixtures belong in `conf/test/<domain>/<ecosystem>/test.conf`; app-local fixture deltas may live beside the app as `conf/apps/<app>/test.conf` or the project-equivalent app path. These files should pin OOD scenario identity and pressure knobs: DAGs, batch slugs, sequences, object keys, target tables, expected inputs, validation toggles, capacity bundles, delete/apply step controls, timeout and poll policy, and cleanup policy. They should not choose the operator action.
- **Minimal Viability Lives In Test Overlays**: Default app configuration should describe the normal best-practice execution contract. Minimal loops, reduced samples, tiny row counts, trimmed fixture batches, short waits, and other "prove the path" pressure settings should be declared in `-t` overlays or explicit transient context packs. Tests should assert both sides when the distinction matters: baseline defaults remain standard, while test mode activates the minimal viable profile needed to exercise real functionality cheaply.
- **Incorporation Tests Prove Ownership Boundaries**: When reviving or copying an app, tests should assert that project-owned buckets/providers resolve from project includes, functional app defaults live in the functional ecosystem, concrete local/workstation ecosystems stay thin, and `-t` activates the miniature fixture. See [App Incorporation](../utility_skills/SKILL_APP_INCORPORATION.md).
- **Test Mode Contract Tests**: Projects that expose `-t/--test` should test the config contract itself: default `test` is false; `-t`, `-t true`, and `-t false` parse predictably; ecosystem test overlays are inactive by default; active test overlays trump developer and ephemeral context while CLI remains final; app `test.conf` extends app baseline only in test mode; test overlays cannot own or override `action`.
- **Abstract Function Independence**: Tests MUST target pure leaf nodes iteratively. Assess module functions by feeding them strictly primitive independent datatypes (URI strings, integer dimensions, explicit configuration dictionaries) rather than demanding massive monolithic DAG Orchestration boots to execute a trivial test slice.
- **Analytical Pruning Parity**: When testing PySpark architectures, assertion testing MUST concretely validate that O(1) query-pruning logic functions correctly against `<global_conf_id>` dimension boundaries, proving the pipeline bypasses irrelevant namespaces.
- **Topological DAG Ordering & `ttX` Nomenclature**: When architecting integration tests for complex pipeline DAGs, you are strongly encouraged to encapsulate tests inside strict chronological domain directories (e.g., `tests/01_core/`, `tests/02_preparation/`) to physically enforce architectural evaluation boundaries within PyTest. Additionally, developers are strongly encouraged to prefix test scripts natively with topological tiers (e.g., `test_tt1_orchestrator.py`, `test_tt2_preparation.py`) reflecting their distinct functional depths. This guarantees PyTest organically executes foundational pipelines before touching downstream consumers. If the architecture evolves by inserting intermediate domains, developers should aggressively rename and re-number the downstream directories and files. Git tracking should not be a consideration; let Git do what it likes. You should not hesitate to renumber downstream architectures strictly to preserve raw `git log / git blame` history. Architectural accuracy, pure linear iteration, and the strict mathematical representation of the pipeline generally supersede historical file tracking.
- **Human-Readable Evidence Reports**: Tests that bridge ontologies, classify input, call an external endpoint, or validate a live/message-driven path MUST produce a concise evidence report that a human can read without reverse-engineering the fixture. The report should be generated by reusable code, not hand-spliced ad hoc in each test, and should identify:
    1. the input object under test;
    2. the app function, endpoint, topic, or storage path exercised;
    3. the resolved config/query parameters that materially affect the call;
    4. the relevant returned payload or a bounded preview of it;
    5. the derived classification, unique id, output path, or failure state.
- **Reactive Distributed Integration Reports**: Integration tests for reactive distributed ecosystems, such as storage-event, topic, queue, pub/sub, fanout, and downstream-ingestion workflows, MUST model progress as explicit observable nodes rather than ad hoc log strings. The progress/evidence contract should live in a shared module owned by the test/workflow family, with an explicit name such as `flow_contract`, `progress_contract`, or `evidence_contract` rather than a generic `steps` bag, and each client should render the subset it actually exercises.
    - For the fuller harness pattern, use [Reactive Distributed Integration Testing](SKILL_REACTIVE_DISTRIBUTED_INTEGRATION_TESTS.md).
    1. Step names must describe the observable contract in human terms, for example `Provider smoke file found in S3`, not vague aggregate states such as `Destination blobs present`.
    2. Aggregated checks must decompose into per-resource or per-surface evidence when the operator needs to diagnose where the chain stopped.
    3. Each step should carry its own expected resource locations, callback URLs, topic names, execution URLs, or other view links when they exist.
    4. Event callbacks should mark only the step they prove. Observing a topic message, destination check, or job snapshot must not imply unrelated downstream success.
    5. If provenance or run ids exist, filter asynchronous evidence by that id before marking progress. Queue clutter and old events are test noise, not proof.
    6. Reactive producers should use the shared Wielder topic/event envelope for serialization and provenance transport rather than hand-assembling bespoke event dictionaries in each domain app.
    7. If a workflow deliberately does not continue, for example because the upstream mirror had no changes, downstream steps should be `skipped` with that reason rather than left pending.
    8. Long-running observers should accumulate a final readable report and structured artifact at the end, including time checked, exact key/path, found/not found state, and the next human-inspectable link.
- **Reports Do Not Replace Assertions**: Evidence reports are observability surfaces. Tests must still assert the behavioral contract directly: expected classification, exact endpoint/query shape where important, expected output count, unique id, ambiguity state, deletion result, or TDD failure condition. Use `pytest -s` when the operator needs to see the report in the terminal.
- **Readable Assertion Ledger**: When a test is intended as an operator handoff or executable evidence report, each assertion should emit a concise human-readable PASS/FAIL line describing the contract under test, surrounded by a preceding and trailing blank line. Implement this with a small reusable assertion helper owned by the test module or test family so assertion output is uniform and failures still raise normal pytest `AssertionError`s. Pair the handoff command with `-s` so passing assertion ledgers are visible.
- **Function-First Test Shape**: Prefer tests that construct a representative event/input, call the app or project-level function that owns the behavior, and assert the output. Avoid making pytest a thin wrapper around CLI argument parsing unless the CLI boundary itself is what is under test. For Wielder-managed scripts, modes and ecosystem context should come from Wielder action/config semantics rather than bespoke test-only CLI flags.
- **Root-Addressable Test Commands**: When handing a pytest command to the operator, give it as a single-line command with absolute or root-resolvable test paths, e.g. `pytest $HOME/workspace/domain-lib/tests/assay -q`. Use `$HOME` for contextual operator-home paths rather than machine-specific literals such as `/home/gideon`. Do not require `cd` or a multi-line setup sequence. Add `-s` only when human report output is intentionally part of the handoff.
- **Documented Live Test Surfaces**: Projects with live integration tests, especially tests that seed `-t` fixtures or start a local API/server, should maintain a small test index beside the tests, such as `tests/TESTS.md`, in the same style as notebook or exploration indexes. The index should point directly at the fixture harness and primary test modules, name the configured test-mode identities, state which real app/service paths create missing data, and provide root-resolvable full-suite and live-surface commands. This keeps the integration philosophy visible to operators instead of hiding it inside pytest fixtures.
- **Nudnik Pattern**: A Nudnik is a wieldable, scalable, scenarioable, workflowable test component that repeatedly exercises a real workflow with named scenarios. It is not merely a pytest fixture, and it is not a mock architecture. Use the Wielder scaffold in `wielder.nudnik` (`Wielder/wielder/nudnik/nudnik.py`) for the generic configurable scalable Nudnik contract. A Nudnik should make scenario, scale/pressure, source, source transport, sink, engine, idempotency, and report surfaces first-class configuration. It should prefer one primitive scenario builder or source reader that returns plain typed payloads, then reuse that same primitive across unit-scale direct execution, futures-style local parallelization, Spark load paths, and topic/event-driven flows. Sources may be generated synthetic payloads, existing events, object-store prefixes, or tables when the goal is replaying real production-like material. Spark is a strong load-testing engine: use it to modulate volume, duplication, partitioning, concurrency, and sink pressure while preserving the real schema and write path. Default Nudnik sinks should be versioned and cleanupable, while developer config can disable cleanup so notebooks can inspect generated outputs.
- **The Multi-Stage Microservice Verification Sequence**: Before finalizing or merging architectural modifications against an orchestrated Wielder service or PyHocon configuration, developers MUST physically assert the entire `WieldService` orchestration pipeline across the underlying infrastructure layer. The universal QA loop entails:
    1. **Plan (`-w plan`)**: Assert the deployment graph PyHocon parsing sequence organically without mutation (Dry-Run). Fix any explicit syntax, fallback, or override issues.
    2. **Delete (`-w delete`)**: Aggressively purge existing namespaces, services, and workloads to enforce isolated evaluation states and test clean deletions.
    3. **Apply (`-w apply`)**: Stand up the live infrastructure completely on the chosen Surface (e.g. `docker`, `aws_eks`). Validate container startup dependencies and ConfigMap bindings.
    4. **Sanity Execution (`sanity.py & pytest`)**: Programmatically strike the established API endpoints (e.g. `gRPC localhost:50051`) with localized integration suites or isolated Python `sanity` probes to prove Data Lake IO and Network boundaries are functionally resolving.
