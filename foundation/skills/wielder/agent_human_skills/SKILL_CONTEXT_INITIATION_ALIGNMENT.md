# Context Initiation Alignment

Establish enough context to act on the user's task without inventing a different
architecture or disturbing unrelated work.

## Required understanding

- Read the host project's safety contract and [Foundations](../../../../FOUNDATIONS.md).
- Verify the selected checkout, branch and relevant worktree changes.
- Identify the owning project and its relationship to Wielder, domain code,
  wielding workflows and execution surfaces.
- Use the [skills catalogue](../../../docs/catalogs/MASTER_SKILLS.md) to read
  instructions relevant to the requested task.

Configuration is the modulation layer through which the same functionality
takes different operational forms. For configuration work, read the
[configuration guidelines](../config_skills/SKILL_CONFIGURATION_GUIDELINES.md)
and [epigenetic contracts](../config_skills/SKILL_EPIGENETIC_CONFIG_CONTRACTS.md).
Do not infer the active ecosystem or context from a directory name.

## Proportional orientation

A known checkout and a clear continuation usually need a fresh status check and
inspection of the relevant files, not a repeated tour of the repository.
Use existing context to locate evidence; verify facts that may have changed.
Read additional documentation when the task crosses a boundary it governs.

Tell the operator the task scope and any consequential uncertainty. A fixed
recap template or a question about whether the task is new is unnecessary when
their request already establishes that.

If the goal is genuinely lost, use
[context recovery](SKILL_CONTEXT_RECOVERY_ALIGNMENT.md). Ask for clarification
only when inspection leaves a material ambiguity about intent, ownership or
authority.

Orientation does not authorize checkout changes, cleanup, commits, deployment
or other mutations beyond the user's request.
